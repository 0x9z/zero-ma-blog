The cut Command: A Linux Beginner's Complete Guide to Extracting Data Like a Pro

6 min read by Zero

I had a file with 40,000 lines. I needed one column out of it — the third one, separated by colons — and nothing else.

My first instinct was Python. Open the file, split each line, grab index 2, write it back out. Ten minutes of code for something that turned out to be a five-second problem.

cut -d: -f3 /etc/passwd

One line. That's the moment cut stopped being "some command I'd seen in tutorials" and became a permanent tool in my terminal.

What cut Actually Does

`cut` extracts sections from each line of a file or input — by character position, by byte, or by delimiter-separated field. It doesn't understand your data the way awk does. It doesn't search like grep. It just slices, cleanly and fast. That narrowness is exactly why it's useful: when a job is "give me column 3," reaching for a bigger tool is overkill.

The Three Ways to Cut

1. By Character Position (-c)

echo "Anas Ait Baani" | cut -c1-4

Output: Anas

-c1-4 grabs characters 1 through 4 from every line. Useful when your data is fixed-width — old log formats, legacy exports, anything where column 12 always means the same thing regardless of content.

2. By Byte Position (-b)

cut -b1-10 file.txt

Almost identical to -c, but counts bytes instead of characters. They only diverge with multi-byte encodings (UTF-8 accents, non-Latin scripts) — for plain ASCII text, treat them as the same tool.

3. By Field, With a Delimiter (-d and -f)

This is the one you'll actually use most.

cut -d: -f3 /etc/passwd

-d: tells `cut` the delimiter is a colon. -f3 says "give me field 3." Change the delimiter to match your data — comma for CSVs, tab for TSVs, space for a lot of command output.

cut -d',' -f1,3 data.csv

Field lists work too: -f1,3 grabs the first and third fields. -f1-3 grabs a range. -f2- grabs field 2 through the end of the line.

Real Situations Where cut Earns Its Place

Pulling usernames from /etc/passwd

cut -d: -f1 /etc/passwd

/etc/passwd is colon-delimited: username, password placeholder, UID, GID, comment, home directory, shell. Field 1 is always the username, no matter how the rest of the line varies.

Extracting an IP from a log line

echo "192.168.1.10 - - [17/Aug/2026] GET /index.html 200" | cut -d' ' -f1

Output: 192.168.1.10

Web server logs are space-delimited by convention, and the client IP is almost always field 1. Pipe a whole log file through this and you've got a raw list of every IP that hit the server.

Pulling just the process name from ps

ps aux | cut -c1-9,64-

Character ranges don't have to be contiguous — combine two ranges to grab the username column and the command column while skipping everything in between.

Getting IPs from ip addr

ip -o addr show | cut -d' ' -f7 | cut -d/ -f1

Notice the chained `cut` here — pipe the output of one `cut` into another with a different delimiter. First pass gets the CIDR block, second pass strips the subnet mask, leaving just the address.

cut vs awk vs grep: Knowing Which Tool to Reach For

grep    -> find lines that match a pattern
cut     -> extract fixed columns/fields from every line
awk     -> extract AND transform, with logic and conditions

If the question is "which lines contain this," that's `grep`. If the question is "give me column 3 of every line," that's `cut` — faster to type and faster to run than reaching for `awk` on a job that doesn't need `awk`'s power. If you need conditions, math, or reformatting, that's when `awk` earns the extra syntax.

I used to jump straight to `awk` for everything, because it can do what `cut` does and more. The habit I had to build was the opposite: default to the smallest tool that solves the actual problem, not the most powerful one available.

A Common Trap: Delimiter That Isn't There

echo "no delimiter here" | cut -d: -f2

If a line doesn't contain the delimiter at all, `cut` prints the whole line back by default. This surprises people expecting an empty result. Add -s to suppress lines that don't contain the delimiter, if that's the behavior you actually want.

What This Tool Taught Me

1. Not every text problem needs a script. The instinct to open an editor and write a parser is often the slow path — the shell already has a tool for "give me this column," and it runs in milliseconds on files a script would take seconds to even load.

2. Chaining beats complexity. Two simple `cut` calls piped together solved the IP-extraction problem faster and more readably than one clever regex would have.

3. Pick the narrowest tool. `awk` can replace `cut`, `grep`, and half of `sed` — but reaching for it by default means writing more syntax than the problem needs. Match the tool to the job, not the job to your favorite tool.

Quick Reference

# By character position
cut -c1-4 file.txt

# By byte position
cut -b1-10 file.txt

# By field, custom delimiter
cut -d: -f3 /etc/passwd
cut -d',' -f1,3 data.csv
cut -d',' -f2- data.csv

# Combine non-contiguous ranges
cut -c1-9,64- file.txt

# Chain cut calls for multi-step extraction
ip -o addr show | cut -d' ' -f7 | cut -d/ -f1

# Suppress lines missing the delimiter
cut -d: -f2 -s file.txt

Final Thought

`cut` isn't glamorous. It won't show up in a highlight reel of impressive one-liners the way a `kill -9` moment might. But it's the tool I reach for almost daily now — quietly, without thinking about it — which is usually the real sign a command has earned a permanent spot in your terminal.
